§ 01

Executive Summary

This document is the consolidated final assessment of a custom-built, multi-entity, IFRS-grade accounting engine deployed on Supabase (PostgreSQL). The system was subjected to a full-spectrum audit across its structural, functional, security, performance, and reporting layers, drawing on direct schema introspection (slime3.json), human-readable schema dumps (slime1/slime2), and the intermediate review document (comprehensive_schema_review_v2.html).

The architecture is sophisticated and clearly inspired by enterprise GL platforms such as Oracle Fusion General Ledger, NetSuite, and SAP FI. It is architecturally sound at the conceptual level — a rare achievement for a custom-built PostgreSQL accounting system. However, before production deployment, six critical issues must be resolved. Left unaddressed, any one of them would produce incorrect financial data, open security holes, or trigger immediate runtime failures.

⚠ This system is NOT production-safe in its current state. All six P1 issues must be resolved and all regression suites must pass before any tenant data is processed.

Overall Scorecard

Referential Integrity Mixed Partitioned parents cannot hold FKs; key constraints are compensated only partially by triggers.

The Six P1 Critical Issues

P1 Critical — Immediate action required
F-01 RLS disabled on all tables despite policies existing Security
Any authenticated Supabase user can read and write every organisation's events, effects, balances, audit logs, and IFRS schedules. Full multi-tenant data exposure. One ALTER TABLE ... ENABLE ROW LEVEL SECURITY per table resolves it.
F-02 post_ecl_year_end() — missing event_type and user_id Runtime Bug

F-03 post_deferred_tax_movement() — missing event_type Runtime Bug
Same pattern as F-02. Deferred tax posting will fail with a NOT NULL constraint violation. Pre-dates the stricter event model; legacy function needs updated signature.
F-04 Audit log hash-chain corruption from duplicate triggers Data Integrity
Two BEFORE INSERT triggers compete to write prev_hash. The second trigger overwrites the value set by the first, breaking chain continuity. The forensic audit trail is silently invalid until this is resolved.
F-05 HASH vs RANGE partition mismatch destroys join pruning Performance
economic_events is RANGE-partitioned by event_date; event_effects is HASH-partitioned by event_id. Every accounting query joining these two tables must scan all 8 hash partitions. Financial statement generation, trial balance, and constraint triggers all degrade to O(N) scans.
F-06 Cash flow statement double-counts year-end closing entries Correctness
generate_cash_flow_indirect() includes retained-earnings sweep entries in net profit calculations. Produces an incorrect Cash Flow Statement for any reporting period after a year-end close.

§ 02

Domain Architecture

The system implements a complete general ledger and financial reporting engine. Its conceptual structure maps faithfully to commercial enterprise accounting platforms and the design choices are well-reasoned throughout.

Event → Effect → Balance Lineage

The core data lineage is modelled as:

Economic Event
   └─ Event Effects  (debits / credits derived from rule engine)
         └─ Account Period Balances  (period-level aggregates)
               └─ Daily Account Balances  (daily rollups)
                     └─ Financial Statement Snapshots  (cached FS output)

This separation of economic intent (event) from accounting consequence (effect) is architecturally correct and enables full auditability. Each event remains immutable and effects are derived deterministically — both principles followed by enterprise GL systems.

§ 04

Referential Integrity Analysis

Your schema uses a hybrid integrity strategy: strict PK/UK constraints on non-partitioned tables, and trigger-based logical enforcement for partitioned fact tables (where PostgreSQL prevents FK references into partitioned roots). This is the correct approach — the design intent is sound. The execution has gaps.

The Partition FK Problem

PostgreSQL cannot enforce a foreign key from a partitioned child table to a partitioned parent root. This means the critical relationship:

-- This FK CANNOT be declared — PostgreSQL limitation
event_effects.event_id  →  economic_events.id   -- both partitioned

Your system compensates with constraint triggers. However, because event_effects is HASH-partitioned, those triggers must scan all 8 partitions on every check — turning what should be a fast index lookup into a full cross-partition scan. The fix is partition realignment (see §6).

Cycle Detection for Entity Relationships

CREATE OR REPLACE FUNCTION prevent_entity_cycle()
RETURNS trigger AS $$
BEGIN
  IF EXISTS (
    WITH RECURSIVE rec AS (
      SELECT NEW.child_entity_id AS id
      UNION ALL
      SELECT er.child_entity_id
      FROM entity_relationships er
      JOIN rec r ON er.parent_entity_id = r.id
    )
    SELECT 1 FROM rec WHERE id = NEW.parent_entity_id
  ) THEN
    RAISE EXCEPTION 'Cycle detected in entity relationship graph';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

Partitioning Architecture

⚠ The HASH vs RANGE mismatch between economic_events and event_effects is the single largest performance problem in this schema. It must be corrected before any high-volume workload is attempted.
TableCurrent StrategyPartition KeyAssessment
economic_eventsRANGEevent_dateCorrect — time-based is ideal for GL
event_effectsHASHevent_idWrong — defeats all join pruning
audit_log_heap_archive_YYYY_MMMonthly RANGEtimestampCorrect — high volume, time-based
economic_events_yYYYYAnnual RANGEevent_dateCorrect
event_effects_p0 … p7HASH (8 buckets)event_idProblematic — incompatible with events

Why HASH Partitioning on event_effects Is Critical

Consider the simplest possible accounting query — joining events to effects for a date range:

SELECT *
FROM economic_events e
JOIN event_effects x ON x.event_id = e.id
WHERE e.event_date BETWEEN '2025-01-01' AND '2025-01-31';

PostgreSQL can prune economic_events to a single yearly partition. But for event_effects, it has no mathematical way of knowing which hash bucket an event_id will land in — so it scans all 8. This affects:

  • Double-entry constraint triggers (O(N) scans on every transaction)
  • Balance propagation triggers (slower commit times under load)
  • Financial statement generation (full cross-partition scan)
  • Trial balance and ledger extract queries
  • All IFRS calculation routines that join events to effects

Correct Architecture: Align Both Tables to RANGE

-- Step 1: Drop all hash child partitions (empty pre-deployment)
DROP TABLE IF EXISTS event_effects_p0 CASCADE;
DROP TABLE IF EXISTS event_effects_p1 CASCADE;
-- ...through p7...

-- Step 2: Recreate root with RANGE partitioning
DROP TABLE IF EXISTS event_effects CASCADE;

CREATE TABLE event_effects (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id   bigint NOT NULL,
  entity_id  bigint NOT NULL,
  account_id bigint NOT NULL,
  event_date date   NOT NULL,
  debit      numeric(18,2),
  credit     numeric(18,2),
  metadata   jsonb
) PARTITION BY RANGE (event_date);

-- Step 3: Create yearly partitions matching economic_events
CREATE TABLE event_effects_2024 PARTITION OF event_effects
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE event_effects_2025 PARTITION OF event_effects
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

After this change, both tables are RANGE-partitioned by the same column and date boundaries. Partition pruning will work for both simultaneously. This is how Oracle Fusion, NetSuite, and Snowflake event-ledger architectures are structured.

Partition Pruning Validation

EXPLAIN

JOIN event_effects x USING (event_id)

SECURITY DEFINER Warning

Several posting functions (post_deferred_tax_movement, post_ecl_year_end, post_manual_journal_event) are marked SECURITY DEFINER. When RLS is disabled, these functions can be called by any authenticated user to insert arbitrary ledger entries with elevated privileges. Resolution:

  • Switch all posting functions to SECURITY INVOKER
  • Reserve SECURITY DEFINER only for admin-controlled period status transitions
  • Add auth.uid() caller-context checks inside all sensitive functions

Remediation Plan

Because the system is pre-deployment, all structural changes can be made without data migration concerns. Apply patches in this exact order to avoid cascading failures.

Mandatory Application Sequence

APB Integrity Validation Suite

The Account Period Balance (APB) table is the nervous system of the GL. If APB integrity holds, the entire ledger is correct. Run all suites after patches are applied — all must return zero rows.

Suite 1 — Double-Entry Balance Check

SELECT event_id,
       SUM(COALESCE(debit,  0)) AS total_debit,
       SUM(COALESCE(credit, 0)) AS total_credit
FROM event_effects
GROUP BY event_id
HAVING SUM(COALESCE(debit,0)) != SUM(COALESCE(credit,0));
-- Expected: 0 rows

Suite 2 — Orphan Effects Detection

SELECT x.*
FROM event_effects x
LEFT JOIN economic_events e ON x.event_id = e.id
WHERE e.id IS NULL;
-- Expected: 0 rows

Suite 3 — No Postings in Closed Periods

SELECT x.*
FROM event_effects x
JOIN reporting_periods p
  ON  p.entity_id = x.entity_id
  AND x.event_date BETWEEN p.period_start_date AND p.period_end_date
WHERE p.is_closed = TRUE;
-- Expected: 0 rows

Suite 4 — APB Continuity (opening + activity = closing)

WITH effects_totals AS (
  SELECT x.entity_id, x.account_id, p.period_start_date AS period,
         SUM(COALESCE(debit,0) - COALESCE(credit,0)) AS net_activity
  FROM event_effects x
  JOIN reporting_periods p
    ON  x.entity_id = p.entity_id
    AND x.event_date BETWEEN p.period_start_date AND p.period_end_date
  GROUP BY 1,2,3
)
SELECT a.entity_id, a.account_id, a.period_start_date,
       a.closing_balance,
       a.opening_balance + e.net_activity AS expected_closing
FROM account_period_balances a
JOIN effects_totals e
  ON  e.entity_id = a.entity_id
  AND e.account_id = a.account_id
  AND e.period = a.period_start_date
WHERE a.closing_balance != a.opening_balance + e.net_activity;
-- Expected: 0 rows

Automated Validation Runner

CREATE OR REPLACE FUNCTION run_apb_validation()
RETURNS TABLE(test_name text, passed boolean, details text) AS $$
BEGIN
  RETURN QUERY SELECT
    'Double-Entry Balance',
    COUNT(*) = 0,
    'Unbalanced events: ' || COUNT(*)
  FROM (
    SELECT event_id FROM event_effects
    GROUP BY 1
    HAVING SUM(COALESCE(debit,0)) != SUM(COALESCE(credit,0))
  ) q;

  RETURN QUERY SELECT
    'Orphan Effects',
    COUNT(*) = 0,
    'Orphans: ' || COUNT(*)
  FROM (
    SELECT 1 FROM event_effects x
    LEFT JOIN economic_events e ON x.event_id = e.id
    WHERE e.id IS NULL
  ) q;

  RETURN QUERY SELECT
    'Effects in Closed Periods',
    COUNT(*) = 0,
    'Violations: ' || COUNT(*)
  FROM (
    SELECT 1 FROM event_effects x
    JOIN reporting_periods p
      ON p.entity_id = x.entity_id
     AND x.event_date BETWEEN p.period_start_date AND p.period_end_date
    WHERE p.is_closed = TRUE
  ) q;
END;
$$ LANGUAGE plpgsql;
